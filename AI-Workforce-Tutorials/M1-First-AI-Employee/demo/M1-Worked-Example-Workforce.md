# M1 — Worked Example Workforces

These examples show what a finished Blueprint looks like, and one that is wrong. Use them for the facilitator demonstration, as a worked example when a learner is stuck after two questions, and as the basis for transfer tasks. Do not hand a learner a completed example before they have attempted their own.

Every example here is fictional or illustrative.

---

## Example 1 — Blueprint Lite for the demonstration workflow (what M1 expects)

**Workflow:** Turn a meeting transcript into a reviewed commitment register.  
**Trigger:** A new meeting transcript is saved.  
**Desired outcome:** A register the human can trust enough to copy into a tracker after review.  
**Human owner:** The meeting organizer.

### Responsibility sort

| Responsibility | Employee | Skill | Tool | Human | Why |
| --- | --- | --- | --- | --- | --- |
| Read the transcript | | | ✓ | | Performs an action (file read) |
| Classify each statement: commitment, conditional, suggestion, decision, context | ✓ | | | | Repeated judgment that the contract makes the employee accountable for |
| Attach a supporting quotation to every row | | ✓ | | | Reusable procedure, applies to any extraction |
| Format the register as a table | | ✓ | | | Procedure, no independent accountability |
| Decide which items to track or escalate | | | | ✓ | Organizational judgment and accountability |
| Update the project tracker | | | | ✓ | Authoritative record; prohibited for the Builder in cohort one |

### Authority map

| Responsibility | A / R / P / X | Reason |
| --- | --- | --- |
| Read the designated transcript | A | Inside the contract's designated input path |
| Write `outputs/first-proposal.md` and the receipt | A | Inside the designated output paths |
| Classification and register contents | R | The human reviews before anyone relies on it |
| Contact a participant to confirm Dev's date | X | External contact is prohibited in cohort one; the human does it |
| Update the tracker | X | Authoritative-record update is prohibited in cohort one |

### Topology

**Single bounded employee** (the Conductor acting as Builder). Why: one small slice, one accountable output, no distinct context, permission, or verification need yet. Evidence that would change this: repeated unsupported classifications that the same employee does not catch in its own review would justify an independent Reviewer in M3.

### Candidate roles, held as hypotheses

| Candidate | Separation benefit claimed | Disappearing-employee test | Earned in |
| --- | --- | --- | --- |
| Reviewer | Independent verification of classifications | Not yet shown; one corrected run is one observation | M3 |
| "Formatter" | None; formatting is a procedure | Fails: a skill does the job with no new context or permission problem | Not an employee |

### Skills needed: evidence citation; commitment classification rules. Tools needed: file read; file write. Human-held: tracker updates; follow-up with participants; priority decisions.

## Example 2 — A workforce that is earned later (weekly competitive intelligence briefing)

This is the end-state a learner might reach by M3 to M6. It is **not** an M1 expectation. It exists to show how an architecture grows from evidence.

**Workflow:** Produce a decision-ready weekly competitive intelligence briefing.

| Role | Owns | Why separate | Earned in |
| --- | --- | --- | --- |
| Conductor | Delegation, prioritization, synthesis, assembling the final briefing | One accountable owner of the final result | M1 (as the single bounded employee) |
| Builder (research) | Investigates high-value signals and produces evidence-backed findings | Source-heavy context that would crowd the Conductor's working context | M2–M3, if run evidence shows context overload |
| Reviewer | Challenges unsupported conclusions and overconfident claims | Independent verification; cannot approve its own work | M3 |
| Observer | Proposes one testable improvement from approved history | Separates improvement from production execution | M6 |

**Skills:** source-quality scoring; briefing format; evidence citation; weekly comparison template.  
**Tools:** web search; internal document retrieval; shared drive; document writing.  
**Human-held:** publication; external communication; strategic decisions; changes to monitoring priorities with material consequences.

### The discussion question

"Would 'Briefing Formatter' deserve to be Employee 5?" Usually no. Formatting is a reusable procedure and passes the disappearing-employee test, so it is a skill.

### Notes on the example's mapping

- A "signal scout" that monitors sources and a "research analyst" that investigates them are, for a small first workforce, both candidates for a single Builder with two skills. Separate them only if run evidence shows the monitoring and the investigation need different context, tools, or permissions.
- The research notes list open-ended market intelligence under peer / blackboard coordination, and list their manager–worker examples mostly in software engineering. Choosing a manager as coordinator here is a **course-design choice** that keeps ownership clear and matches the course's Conductor / Builder / Reviewer reference topology. It is not a finding that manager–worker is best for this workflow.
- The course never requires this many roles. A learner who stays with one Builder and good skills can pass.

## Example 3 — Over-built (use as a transfer or "find the problem" task)

A learner proposes this workforce for a one-page weekly status brief: Researcher, Summarizer, Rewriter, Formatter, Reviewer, and Manager.

### Diagnosis questions

1. Which of these differ in context, tools, or permissions, and which differ only in the prompt?
2. Run the disappearing-employee test on each. Which fail?
3. Which responsibilities does nobody clearly own?
4. What is the coordination cost of six handoffs for one page of output?

### One defensible repair

- One bounded employee owns the brief (research, summary, rewrite).
- Formatting and source scoring become skills.
- A Reviewer stays a **hypothesis** until run evidence shows unsupported claims that the author does not catch.
- The Manager role disappears: with one employee, the human is the manager.

### What a learner should say

"I'd keep one employee and two skills. I'd add an independent reviewer only if I saw unsupported claims getting through, because the reviewer's value is independence, and I haven't shown I need it yet."

An equally defensible answer keeps a Reviewer from the start with a stated verification reason. The scoring question is whether each kept role is justified by a separation benefit, not whether the learner matches a number.
