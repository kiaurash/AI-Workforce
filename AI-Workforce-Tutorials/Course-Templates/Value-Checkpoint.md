# Value Checkpoint

One entry per module, in one file: `runs/value-checkpoint.md`, starting from M1. See Course.md section 4.2.

The question: *Did what we added in this module make the workflow better enough to justify what it cost?*

```markdown
# Value Checkpoint: [Module]

Date: [...]

## In class (about two minutes; three lines)
Judgment: [keep | simplify | remove]
One supporting observation from my own run: [...]
One uncertainty (what more evidence would change my judgment): [...]

## Between sessions (complete when the evidence is available)
| Measure | Before this module | After this module |
| --- | --- | --- |
| Human time per run | [range; estimate/measured] | [range; estimate/measured] |
| Output usefulness (what the recipient needs) | [...] | [what the recipient or I judged] |
| Rework before relying on the output | [typical corrections] | [corrections recorded] |
| Overhead added (setup, checking, maintenance minutes) | none | [range; estimate/measured] |

Baseline source: [M0 Opportunity Map / M1 workflow card]
Number of runs behind the "after" column: [n]
Evidence paths: [...]

## Decision
[Keep / simplify / remove] [what]. 
If I am removing a control: the risk it covered was [...]. The human approval boundary stays regardless of cost.
```

Rules:

- Estimates and ranges are fine. Do not report precision that one or two runs cannot support.
- "Not worth it" is a valid judgment.
- Assessment checks that your judgment cites your own run evidence. It does not grade the numbers.

## Illustrative example after M3 (fictional)

```markdown
Judgment: keep, conditionally
One supporting observation: the Reviewer caught one unsupported claim in run 1 but added eight minutes of review (measured, one run).
One uncertainty: I need several more runs to know whether it earns that time on routine reports.
Decision: keep for reports going to senior management; review the rest with my checklist.
```
